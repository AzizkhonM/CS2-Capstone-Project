01 Problem / User

Seeding is guesswork. It shouldn't be.

CS2 tournament organizers — including my own tournament management platform — currently seed brackets manually and subjectively, with no data-backed way to justify placements. This causes strong teams to face each other in early rounds by chance, and leaves organizers unable to defend decisions when teams dispute their seed.

The model reaches 84.1% AUC on real, unseen matches — but the point isn't the number. It's that every seed now comes with a reason an organizer can point to.

02 How it works
01

Self-built Elo, verified correct

Computes a time-ordered Elo rating from 7,033 historical matches — sanity-checked to confirm teams win 32.4 points more often than they lose, on average, before it's trusted as a signal.

02

19 dynamic features, not 140 raw columns

Combines Elo with recent form, head-to-head history, per-map win rates, and LAN/Online performance — after discovering and removing 76 "static" columns that silently leaked no real signal.

03

Every pair, not just one guess

Predicts a win probability for every possible pair among the selected teams, then averages each team's results into a Power Score used for seeding.

04

Live, not just a notebook

Served through a FastAPI backend deployed on Render, rendered in a custom animated frontend — a working application, not only a Colab cell.

04 Limitation
Documented, not hidden

The model is a decision-support tool, not a final authority — organizers stay in control. Roster changes aren't tracked in real time, and teams with sparse match history get a visible confidence flag.

Interestingly, testing showed sparse-history matchups were actually easier to predict (93.3% accuracy) than matchups between established teams (72.6%) — a result that contradicted my original assumption and reshaped how the limitation is documented.

05 Model Roadmap

One pair in. One probability out.

The model is not multi-team — it's a pairwise classifier. It only ever compares two teams at a time, and everything below happens inside that single comparison, step by step.

01

Input — a single pair, 19 numbers

The model never sees team names. It receives 19 numeric features — each one a difference between the two teams, computed as team1_value − team2_value (e.g. elo_diff = 1948 − 1500 = 448): elo_diff, past3_diff, head2head_percentage_diff, head2head_freq_diff, mirage_diff, inferno_diff, nuke_diff, dust2_diff, overpass_diff, train_diff, ancient_diff, vertigo_diff, anubis_diff, wins_diff, losses_diff, totalwinrate_diff, online_winrate_diff, lan_winrate_diff and overall_winrate_diff.

02

Scaling

All 19 values pass through a StandardScaler. Raw scales aren't comparable — elo_diff can range roughly −600...+600 while totalwinrate_diff sits in −1...+1 — so every feature is normalized before the model is allowed to weigh them against each other.

03

The model itself — Logistic Regression

Each feature gets a learned coefficient (weight): z = w1·x1 + w2·x2 + ... + w19·x19 + bias. The model simply combines the 19 numbers linearly, then passes the result through a sigmoid: P(team1 wins) = 1 / (1 + e^−z).

04

Output — a single number

The pipeline ends with one value, e.g. P(team1 beats team2) = 0.68. The model never declares a winner — it only ever returns a probability.

Built end-to-end, solo — and stress-tested until it broke.

From auditing 140 raw dataset columns and catching a tournament-bracket seeding bug (top seeds were meeting before the final) to deploying a working API and reproducing the entire pipeline from a fresh clone on a second machine.
